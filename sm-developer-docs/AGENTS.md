# Stone Memory 开发约束

本文供参与 Stone Memory 开发的人类与编码 Agent 阅读。修改代码前必须先理解现有架构，不得根据单个报错自行重写核心流程。

## CLI 是唯一正式写入口

`stmem` CLI 是所有正式状态变更的公共接口。

```text
终端 ────────────────→ stmem CLI → 正式写逻辑
前端 → 本地 HTTP 适配 → stmem CLI → 正式写逻辑
MCP ─────────────────→ stmem CLI → 正式写逻辑
自动任务 ────────────→ stmem CLI → 正式写逻辑
```

- 新写功能必须先有可独立运行、可校验或可 dry-run 的 CLI 命令，再接前端或MCP。
- HTTP层只负责接收参数、创建安全临时文件、调用CLI并格式化结果。
- 不得在前端、MCP或临时脚本中复制初始化、导入、挖掘、压缩、重建和修复算法。
- 只读查询可以调用 reader、parser或planner；确认写入时必须回到CLI。
- API Key不得放入命令行参数、日志、Issue、测试夹具或提交记录。

正式入口包括：

```text
创建/更新记忆体  stmem init
导入对话         stmem import
同步对话         stmem sync
记忆挖掘         stmem mine
摘要压缩         stmem compact / stmem compress
长期隐藏         stmem hidden
线程重建         stmem rebuild
数据库维护       stmem db
系统自检         stmem doctor
```

## 禁止AI自作主张配置

- 禁止直接手写或修改 `~/.stone_memory/stmem.json`。
- 初始化必须先使用 `stmem init --template` 获取机器可填写模板。
- 填写后先执行 `--validate`，通过后再正式创建或更新。
- `threadId`必须是真实的Claude/Codex线程标识，不能填写人物名、记忆体名字或猜测值。
- `sessionDir`是递归搜索线程文件的根目录；找不到对应线程文件时必须停止并报告。
- 不得擅自禁用rebuild、替换备份机制或创建“效果相同”的旁路注入。

## 数据职责

```text
SQLite messages       清洗后的纯对话，是全量对话页和miner的正式输入
SQLite feelings       摘要语义、importance、压缩状态和锚点关联
SQLite features       值得长期关注的高价值概念索引
archive/full          原始线程记录备份，供rebuild和故障恢复使用
活动线程JSONL         当前Agent实际读取的上下文
```

- SQLite是正式结构化数据源。
- `full`保留原始线程记录，不得受纯文本入库规则控制。
- `<memory_context>`和规则注入属于重建产物，不得重新进入纯对话或miner。
- thinking、系统元数据和工具记录不能冒充普通对话写入messages。
- 任何迁移必须说明会修改哪些数据，并为历史用户提供自动修复或明确迁移命令。

## 设计理念与有意保留的边界

Stone Memory不是“把所有文本塞进向量库，再等待相似度召回”的记忆插件。它选择保存可见、可检查、可解释的记忆层，并明确告诉用户哪些内容会进入线程、哪些内容被压缩、哪些内容仍可从原文回查。

### 为什么分成对话、摘要和特征三层

三层数据回答不同问题：

```text
messages  → 当时究竟说了什么
feelings  → 这段经历留下了什么可持续理解
features  → 哪些概念值得沿时间继续追踪
```

- 原文是事实证据，不能让模型生成内容反过来覆盖。
- 摘要保存事件语义、感受、时间和importance，是线程长期记忆的主要载体。
- 特征只负责建立高价值索引和category，不重复保存完整语义。
- 时间曲线、共同签名和生命周期判断必须回到真实对话与摘要交叉验证，不能只看某个词出现了多少次。

不要把三层合并成一张“万能记忆表”，也不要让features取代feelings或原文。

### 为什么特征库当前不提供自由编辑

前端没有给features做普通文本编辑器是有意设计，不是单纯漏做。

- feature是miner从某天对话中产生的派生索引，不是用户亲手写的人设或事实卡片。
- 单独改feature文本不会同步改变原始对话和对应摘要，会让“索引—证据—语义”三层失配。
- 下一次重挖同一天时，人工改写还可能被正式挖掘结果覆盖。
- 生命周期依赖feature的category、来源日期和对应摘要证据；随手改词可能制造虚假的跨库命中或时间曲线。

发现feature错误时，应先判断是单次模型bad case、category提示词问题还是历史数据污染。正式修复方向是改miner规则后重挖对应日期，或通过专门的CLI校正能力完成可追溯修改；禁止前端直接更新SQLite。

规则、人设、摘要文本、摘要状态和人工锚点属于用户需要明确控制的内容，可以提供受控的增删改查；features仍应保持“可查看、可解释、可重新生成”的派生索引定位。

### 为什么不用embedding作为唯一记忆源

embedding适合辅助检索，但相似度返回不等于记忆正确：

- 可能召回语义相近但事件无关的内容。
- 很难解释为什么某条记忆被保留、压缩或遗漏。
- 无法独立表达事件发生时间、关系阶段和项目生命周期。
- 用户难以直接检查并纠正向量空间中的错误关联。

Stone Memory可以在未来把embedding作为搜索辅助，但不能让它成为唯一正式数据源，也不能用它替代日期、摘要、category、importance、锚点与真实原文。

### 为什么完整摘要content永久保留

`daily`、`coarse`和`hidden`描述的是线程注入颗粒度，不是数据库销毁等级。

- coarse只生成更短的注入文本，原始content仍保留。
- hidden只表示rebuild时不注入，记忆搜索和人工检查仍可以找到原内容。
- 用户手动恢复、重新压缩或未来升级算法时，需要原始摘要作为证据。
- 自动压缩不能用不可逆删除换取短期上下文空间。

因此不得把coarse实现成覆盖content，也不得把hidden实现成删除数据库行。

### 为什么有两种锚点

- 原文锚点用于在线程中注入对应的真实对话，保存语气、措辞和上下文。
- 事件锚点用于保护关键摘要不受自动衰减与压缩决策影响。

两者解决的问题不同，不能合并成一个模糊的“重要”开关。人工锚点优先级高于自动生命周期模型；用户移除锚点后，摘要才重新进入自动决策范围。

### 为什么压缩不能只看importance

importance描述单条事件在当时的重要程度，但不能独立回答它在长期记忆中的位置。

- 曾经重要的阶段事件，随着关系或项目推进可能只需保留简写。
- 低频事件可能是长期反复回访的关系课题。
- 普通饮食或身体事实与关系、项目共同出现时，可能由更高层生命周期接管。
- 不同用户的副核心可能是work、preference、eat或其他category，不能写死同一套轻重顺序。

正式压缩需要交叉使用category、时间曲线、摘要共同签名、importance、关系/项目阶段和人工锚点。曲线负责提供证据，不得单独一票决定keep、coarse或hidden。

### 为什么保留CLI、预览和二次确认

初始化、导入、裁剪、压缩和重建都会影响用户长期积累的数据。CLI、dry-run、备份和确认不是多余步骤，而是让前端、MCP、自动任务和人工操作共享同一套安全语义。

不要因为某个Agent认为“自己处理更安全”，就绕开Stone Memory已有的预览、校验和备份机制。

### 为什么避免不断增加状态与模型变量

Stone Memory优先从现有原文、摘要和特征中重算解释，不为每个推断结果建立永久字段。

- 可重算的信息不重复存储。
- 只读建议不应偷偷变成数据库真相。
- 新变量必须能够解释多个真实bad case，而不是只修一个词或一个用户。
- 能用同一生命周期模型解释的现象，不拆成大量用户需要维护的类型。

遇到新场景时，先验证现有证据是否足够，再决定是否扩展模型。

## 线程重建

- Claude和Codex拥有不同线程格式，但必须共享同一套摘要选择、锚点、窗口和安全策略。
- rebuild必须先支持dry-run，再允许apply。
- apply前必须备份活动线程；输出必须经过结构校验后再原子替换。
- 原文锚点与事件锚点受保护；hidden摘要不进入注入候选。
- 水位线模式只替代活跃对话日窗口，不能擅自改变工具链保留设置。
- 修复一条runtime通道时必须检查另一条通道是否存在同类问题。

## Miner与压缩

- miner只读取清洗后的纯对话，不读取full原始文件。
- API和Subagent必须使用相同任务定义与输出约束。
- 大输入按完整消息和真实对话空档分块，禁止截断单条消息。
- 分块失败不得发布部分结果。
- feelings必须保留完整日期和对应时间，并按事件时间稳定排序。
- 压缩不得覆盖原始content；coarse与hidden只改变线程注入颗粒度。
- 原文锚点和事件锚点不受自动压缩与隐藏规则影响。

## 开发流程

1. 复现问题并记录runtime、命令、输入范围和实际错误。
2. 查找现有CLI与共享服务，确认问题发生在哪一层。
3. 先修共享逻辑，再修Claude/Codex或前端适配。
4. 为bad case增加回归测试。
5. 运行相关测试和完整 `npm test`。
6. 提交PR，说明风险、验证结果及是否涉及数据迁移。

## 前端实验模块

- 开发者模式中的实验前端必须遵守 [前端实验模块规范](frontend-modules.md)。
- 采用 `theme-studio` 的可拆卸 bootstrap 结构；模块入口、页面和业务状态不得硬编码进主 `app.js`。
- 入口卡片统一复用 `developer-experiment-card`、`developer-memory-stack` 和 `developer-enter`，通过 `data-module-order` 排序。
- 绑定记忆体的模块只能消费宿主提供的真实 `threadId`，不得自行默认第一套记忆体。
- 实验页面使用 `--stone-theme-*` 主题契约，让主题工作台的修改自动覆盖所有模块。

禁止：

- 遇到报错就另写导入、清洗或rebuild脚本。
- 为单个用户的词语、路径或人物关系硬编码规则。
- 绕过CLI直接改数据库或配置。
- 在没有真实样本验证时增加复杂状态、阈值和自动决策。
- 删除用户数据、锚点或备份却不提供预览和确认。

如果现有架构无法支持需求，请提交Issue或proposal说明缺口，不要用旁路代码假装已经完成。
